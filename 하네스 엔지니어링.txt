하네스 엔지니어링(Harness Engineering)은 대규모 언어 모델(LLM)이 단순한 질의응답을 넘어 실제 업무를 자율적으로 완수하는 AI 에이전트(AI Agent)로 작동할 수 있도록, 모델 바깥의 실행 환경·도구·검증·안전장치를 설계하고 구축하는 엔지니어링 분야입니다.

업계에서는 이를 다음과 같은 공식으로 요약합니다.

> **AI 에이전트(Agent) = 모델(Model) + 하네스(Harness)**

원래 '하네스(Harness)'는 말의 가슴과 몸통에 채워 움직임을 제어하는 마구(馬具)나, 소프트웨어 공학에서 하위 코드를 테스트하기 위해 감싸는 골격 코드(Test Harness)에서 유래했습니다. AI에서는 모델이라는 강력한 '두뇌'가 폭주하거나 길을 잃지 않고 현실 세계와 안전하게 상호작용하도록 감싸는 **'몸'이자 '운영체제(OS)'** 역할을 합니다.

---

### 1. 프롬프트·컨텍스트 엔지니어링과의 차이

AI 엔지니어링의 패러다임이 단일 대화에서 장기 자율 작업으로 넘어가면서 개념이 확장되었습니다.

| 구분 | 프롬프트 엔지니어링 | 컨텍스트 엔지니어링 | 하네스 엔지니어링 |
| --- | --- | --- | --- |
| **핵심 초점** | 단일 질문에 대한 **출력 품질 최적화** | 모델이 한 번에 볼 **정보의 선택·압축·배치** | 에이전트가 작동하는 **실행 환경·규칙·검증 루프 구축** |
| **작동 범위** | 1회성 대화(Single-turn) | 세션 내 메모리 및 RAG 검색 범위 | 수십~수백 단계의 **장기 자율 실행 및 복구** |
| **제어 방식** | 자연어 지시(확률적 의존) | 문서 구조화, 요약(Compaction) | 코드, 스키마, 린터, 권한 정책(결정적 강제) |

프롬프트나 컨텍스트가 "모델이 더 잘하게 만드는 일"이라면, 하네스는 "모델이 실수하거나 환각을 일으켜도 전체 시스템이 무너지지 않고 스스로 고치며 버티게 만드는 일"입니다.

---

### 2. 하네스 엔지니어링의 핵심 구성 요소

실무(프로덕션) 수준의 AI 에이전트 하네스는 크게 다음 요소들로 구성됩니다.

* **가이드 (Guides / Steering):** 에이전트가 작업을 시작하기 전 읽는 프로젝트 규범입니다. 최근 코딩 에이전트에서 많이 쓰이는 `AGENTS.md`, `CLAUDE.md`, `.cursorrules` 파일이 대표적입니다. 추상적인 조언 대신 빌드·테스트 명령어, 수정 금지 경로 등 과거의 실패를 예방하는 구체적 지침을 담습니다.
* **도구와 게이트웨이 (Tools & Gateway):** API 호출, 코드 실행, DB 조회 등 외부 세계와 연결하는 통로입니다. 모델이 도구 실행을 요청하면 하네스는 스키마를 검증하고, 격리된 샌드박스에서 실행한 뒤, 방대한 날것의 로그 대신 모델이 추론하기 쉬운 구조화된 결과(Observation)로 정제해 돌려줍니다.
* **센서와 검증 루프 (Sensors & Verification):** 에이전트의 결과물을 객관적으로 검사하는 피드백 채널입니다. AI는 자기 결과물을 관대하게 평가하는 경향(자기 평가 편향)이 있으므로, 비용이 비싼 LLM 판정보다 **린터(Linter), 타입 체커, 유닛 테스트 같은 빠르고 결정적인(Deterministic) 검증기**를 먼저 배치해 실패 시 에러 로그를 쥐여주고 재시도시킵니다.
* **영속 메모리 (Persistent Memory):** 모델은 매 호출마다 기억을 잃기 때문에, 하네스가 작업 상태를 외부에 기록합니다. 복잡한 DB 대신 `plan.md`(계획), `progress.json`(진행 체크포인트) 같은 파일시스템을 활용해 중간에 세션이 끊겨도 이어서 작업할 수 있게 합니다.
* **권한·예산·가드레일 (Permissions & Budgets):** 안전은 모델의 착한 심성이 아니라 코드로 강제합니다. 최소 권한 원칙에 따라 읽기/쓰기 경로를 제한하고, `git push`나 결제·데이터 삭제 같은 위험 작업 전에는 사람에게 승인을 요청(Human-in-the-loop)합니다. 또한 무한 루프나 요금 폭탄을 막기 위해 최대 재시도 횟수(예: 3회), 실행 시간, 토큰·비용 상한선을 강제합니다.
* **관찰 가능성 (Observability):** 에이전트가 어떤 근거로 어떤 도구를 호출했는지 전 과정을 추적(Tracing)하여 디버깅하고 성능 저하를 감지합니다.

### 3. 왜 지금 주목받고 있는가?

1. **'데모'와 '실무(프로덕션)'의 간극 해결:** 시연 영상에서는 완벽해 보이던 에이전트가 실제 업무에 투입되면 컨텍스트가 길어지면서 앞선 지시를 잊거나(Context Rot), 창 한계에 다다랐다고 느껴 작업을 대충 마무리하는 현상(Context Anxiety)이 빈번하게 발생합니다. 하네스는 이를 구조적으로 제어합니다.
2. **모델 교체 없이 성능 극대화:** 기반 모델(Foundation Model)의 성능이 상향 평준화되면서, 이제는 같은 모델을 쓰더라도 "누가 더 탄탄한 검증 루프와 도구 환경을 짰는가"가 에이전트의 실전 완성도를 결정합니다.

> **💡 핵심 설계 원칙:** 하네스의 구성 요소는 모델의 한계를 보완하기 위해 존재합니다. 따라서 차세대 모델이 출시되어 기존에 하네스가 막아주던 실수를 모델 스스로 하지 않게 되면, 불필요해진 하네스 코드는 과감히 삭제하며 시스템을 가볍게 유지(Recalibration)하는 것이 중요합니다.
